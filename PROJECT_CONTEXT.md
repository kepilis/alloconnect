# alloconnect — контекст Windows-клиента

Снимок исходников от 24 ноября 2026 г. Версия приложения в `package.json` и `package-lock.json` — **1.22.12**, Electron по lock-файлу — **44.9.1**. В `README.md` и `CLAUDE.md` фигурирует 1.22.7. Это Windows x64-приложение для связи с друзьями, ранее называлось `alocalls` и `Duo`. Основной режим — прямое соединение. Хостинг исходников, релизов и подписанных обновлений указан в `GH_REPO` в `main.js`. В этой копии есть общие адаптеры для телефона. Карта Android-клиента, сборки и результаты совместных тестов в [ANDROID_CONTEXT.md](ANDROID_CONTEXT.md).

## Точки входа

- `npm start` → `main.js` → главное окно `index.html`. `preload.js` публикует `window.duo` через `contextBridge`: UI вызывает IPC, Electron main работает с ОС, файлами и сетью. `index.html` задаёт порядок обычных скриптов. `renderer.js` держит общую логику и состояние `S`; `camera.js`, `windows.js` и `stickers.js` загружаются после него. У оверлея и уведомлений свои HTML, скрипты и preload.
- `main.js` также управляет запуском, треем, хоткеями, выбором источника экрана, нативным помощником, локальными данными, обновлениями и загрузкой медиапакетов. При изменении IPC проверяй обе стороны `preload.js` ↔ `main.js` и вызов из UI.
- `native/alloconnect-helper.cpp` и готовый `native/alloconnect-helper.exe` отвечают за звук Windows (Process Loopback), отслеживание окна, приглушение, глобальные клавиши, ввод и замену ресурсов при обновлении. ViGEmClient лежит в `native/vendor`; для виртуального геймпада на принимающем ПК нужен ViGEmBus. Команда сборки C++ в `README.md`.

## Данные и совместимость

- `%APPDATA%\alloconnect` — стандартный профиль. `main.js:migrateLegacy` переносит старые данные из `alocalls` при первом запуске. `ALOCALLS_USERDATA` задаёт отдельный профиль и разрешает несколько экземпляров для проверок.
- Идентичность, друзья, коды, очередь и настройки хранятся в профиле. У renderer есть `localStorage` с префиксом `duo.`. История на диске — `history/<id>/log.jsonl` и `media/`. Статусы и операции правки/реакций хранятся как события. Локальное сохранение вложений ограничено отдельно от передачи.
- Запись связанного аккаунта — `account-lab-record.json`, копии для восстановления — IndexedDB. Сохранённая сессия YouTube — `youtube-session.enc`. Логи находятся в `logs`; для диагностики используй метаданные событий без личного содержимого.
- Уточняй изменения форматов и возможностей на обеих сторонах. Для устаревших клиентов и Android сначала смотри обработку старых приглашений, формат данных и согласование поддерживаемых возможностей. Тестам Android нужен отдельный каталог `../alloconnect_android` или `ALLOCONNECT_ANDROID`.
- Канал друзей пробует до трёх предыдущих адресов, с которых за последние две минуты пришли аутентифицированные UDP-пакеты друга. Это помогает, когда с нового адреса пакеты приходят, а ответы до него не доходят. Дополнительные адреса хранятся в памяти. Запись последнего наблюдаемого адреса на диске и формат пакетов `ALC1` прежние.
- Присутствие и восстановление канала друзей используют разные признаки. Входящий пакет обновляет присутствие. Для завершения восстановления нужен ответ `pong` или ACK пакета, отправленного этому другу. При смене интерфейсов подтверждение сбрасывается. Проверка сети показывает двустороннюю связь после `probe-ok`. При одной входящей пробе сообщает только о приёме.
- В рабочей Windows-копии минутное событие `friends-net` учитывает число попыток отправить ACK (`ackReplies`), полученных ACK (`ackReceived`), подтверждённых ожидающих пакетов (`ackMatched`) и UDP-пакетов, исчерпавших попытки доставки (`deliveryTimeouts`). Эти поля помогают сверять журналы двух сторон без адресов, идентификаторов пакетов и содержимого сообщений. Одна попытка отправить ACK может использовать несколько маршрутов.

## Проверка и сборка

- Обычный запуск `npm install` → `npm start`. Сборка `npm run dist`. В `package.json` нет единой команды `npm test`. Список сценариев и настройка старых тестов описаны в `tests/README.md`.
- Для настольных регрессий без Android используй `node --test --test-name-pattern="desktop|account storage" tests/audit/regressions.test.cjs tests/audit/no-adb.test.cjs`. Основные сценарии Electron — `tests/two-windows/run.js`, `tests/two-windows/run18.js`, `tests/group/run.js`, `tests/group/run-gcam.js`, `tests/group/run-fwd.js`, `tests/friendcode/run.js`, `tests/rejoin/run.js`. `tests/lib/roles.js` создаёт копию приложения и раздельные профили для ролей. Аргумент папки теста должен указывать на одноразовый каталог: подготовка удаляет его перед запуском.
- Точечные наборы есть для UDP/STUN/VPN, уведомлений и интерфейса, истории и очереди, обновлений, камеры, производительности, голоса, клипов и YouTube. Часть старых сценариев содержит жёстко заданные пути, некоторые STUN-тесты принимают `ALLOCONNECT_DESKTOP`. `tests/media-ui`, `tests/replay` и часть тестов клипов требуют FFmpeg/FFprobe по ожидаемому пути. Для нативного `tests/duck/native.cjs` нужно собрать аудиофикстуру.
- В данном рабочем каталоге нет `.git`, `node_modules`, Node и npm в `PATH`. Для аудита найден Electron 44.9.1 в `dist/updates-work/runtime/alloconnect.exe`. В режиме `ELECTRON_RUN_AS_NODE=1` он выполняет Node-тесты. Для тестов с подставным `app.asar` использовался `ELECTRON_NO_ASAR=1`. Для оконных тестов использовалась отдельная копия Electron `default_app.asar` без упакованного приложения и временные профили под `dist/`. В песочнице Codex Windows блокировал запуск Electron и мешал локальным UDP-тестам. За её пределами оба типа сценариев запускались.
